## 1. What This Repository Is

Himinbjörg is server-only ASP.NET Core Identity + OpenIddict persistence and its gRPC front door — no longer just "EF persistence," that framing is obsolete since `Identity.csproj` was deleted 2026-07-23 (`Adios Identity.csproj & Midgard`). The entity model briefly folded into `Norse.Identity.Web.Server` and was hoisted back out 2026-07-30 into **`Norse.Identity.EntityFramework`** — a Web-SDK-free library, so the migrations service takes the schema without the hosting surface. Nothing here crosses to WASM or MAUI — that boundary is load-bearing, not a convenience. In the dependency chain it rides on Urðarbrunnr's EF foundation and everything below, and — since PR #27 (`feature/identity-web-server`, merged, tagged `v0.0.5`) — it also NorseRefs Heimdall's `AuthN.Services` (the `IAuthenticationService` contract it implements) and `AuthN.Components.FluentUI`: the dependency is no longer one-directional. Yggdrasil's `Hosting.Web.Server` is the confirmed external consumer, calling `AddNorseAuthenticationService(connectionString)` (declared in `Identity.Web.Server/ServiceCollectionExtensions.cs`) to wire `NorseIdentityDbContext`, ASP.NET Core Identity with the `NorseSignInManager` override, the FluentValidation validators, the mediator handlers, and `IAuthenticationService` itself into its process.

**Five projects are live** (four of them shipped, tagged, and published to NuGet; `Norse.Identity.EntityFramework` is the newcomer, not yet shipped): `Norse.Identity.EntityFramework` carries the full ASP.NET Core Identity v3 entity set (`NorseUser`, `NorseRole`, `NorseUserClaim`, `NorseUserRole`, `NorseUserLogin`, `NorseUserToken`, `NorseRoleClaim`, `NorseUserPasskey`), the four `NorseOpenIddict*` entities, and `NorseIdentityDbContext` (Identity and OpenIddict combined via `builder.UseOpenIddict<Guid>()`) — deliberately `Microsoft.NET.Sdk`, not `Sdk.Web`, so `Identity.Migrations` reaches the schema through it without dragging the whole web hosting surface into the migrations service. `Norse.Identity.Web.Server` carries `NorseUserStore`, `NorseSignInManager`, the gRPC `AuthenticationService` implementing Heimdall's `IAuthenticationService` — since the wire-purity amendment to the mediator-pipeline migration (Task 12 of `../Glitnir/docs/Platform/plans/2026-07-27-mediator-pipeline-retires-gateway.md`), a bare `ISender` ctor plus three expression-bodied hydrate-and-send methods, each wrapping the incoming Heimdall wire DTO in a one-line server-sovereign command (`LoginCommand`/`RegisterCommand`/`LogoutCommand`, Asgard's `CommandRequest<TRequest,TResponse>`) that carries `[Authorize(Policy = AuthNPolicies.Public)]` — Heimdall's own `LoginRequest`/`RegisterRequest` wire records carry no mediator marker and no `[Authorize]` at all. `LoginHandler`/`RegisterHandler`/`LogoutHandler` are `IRequestHandler<TCommand, TWireResult>` (handling the command, returning the exact wire result type — `LoginResult`/`RegisterResult`/`LogoutResult` — directly, payload mapping including the deferred-completion-URL lookup lives in the handler now), no longer validate inline (Midgard's `ValidationBehavior` owns that, resolving Asgard's generated `CommandRequestValidator<TCommand,TRequest,TResponse>` pass-through adapter, which reaches through the wrapper and reuses Heimdall's `LoginRequestValidator`/`RegisterRequestValidator` unchanged — no hand-written command validators exist), and are wired — together with those generated adapters, Heimdall's two wire validators, and three `ISenderDispatch` map entries — by Asgard's registration generator's `AddNorseIdentityWebServerHandlers()`, not hand-written `AddScoped` lines, and — not yet fully migrated out to Heimdall's `AuthN.Components`/`AuthN.Components.FluentUI` — the bulk of the original Yggdrasil-scaffolded `/Account` and `/Account/Manage` Razor page tree (`Components/Pages/**`), which Bifröst's open-decisions record tracks as an in-progress component migration, not a finished one. `Norse.Identity.Migrations` is now provider-agnostic (`NorseIdentityMigrationContributor`, no EF migrations of its own); the checked-in `InitialCreate` EF migration and embedded `CreateScript.sql` live per-provider in the sibling `Norse.Identity.Migrations.PostgreSQL` and `Norse.Identity.Migrations.SqlServer` projects, each with its own `IDesignTimeDbContextFactory`, standing up `norse_identity` end to end for either provider.

Identity was chosen as this framework's proving vehicle deliberately: its schema is well-known and its base classes are unforgiving, so if the migrations framework survives ASP.NET Core Identity it survives anything. It nearly didn't survive gracefully — one gotcha worth knowing before touching `NorseIdentityDbContext`: ASP.NET Core Identity decides its schema shape (`Version1` vs `Version3`, i.e. whether the passkey table exists) by reading `IOptions<IdentityOptions>` off the context's `ApplicationServiceProvider`. A caller that registers `NorseIdentityDbContext` without the full `AddNorseIdentity()` DI surface — exactly what the migrations service does, since it only needs the context to migrate — would otherwise silently get `Version1` and lose the passkey table. `NorseIdentityDbContext.OnConfiguring` carries a fallback `IServiceProvider` that forces `Version3` for that path; read the type's doc comment before "fixing" it away.

**The PII protection seam is live (2026-08-04/05, the identity-erasure slice of `../Glitnir/docs/Platform/specs/2026-08-03-pii-primitives-identity-erasure-seam-design.md`).** `NorsePersonalDataProtector` (`IPersonalDataProtector`) wraps ASP.NET Core Identity's own `ProtectPersonalData=true` conversion in AES-256-GCM envelope encryption (`v1:{subjectId:D}:{base64(nonce ∥ ciphertext ∥ tag)}`) over Asgard's per-subject key seam (`ISubjectKeyStore`, keyed by the ambient `SubjectCryptoScope` every write path — `NorseUserManager.CreateAsync`/`UpdateUserAsync` — establishes around the base call); `NorseLookupProtector`/`NorseLookupProtectorKeyRing` back the HMAC blind-index columns (`NormalizedEmail`/`NormalizedUserName`) so lookups still work without ever comparing plaintext. A new `subject_keys` table (Urðarbrunnr's migrations chassis; **permanently non-temporal by ruling**, not by preview-channel defect — see the temporal section below) rides beside `Users`. `NorseUser.PhoneNumber` is bounded to `character varying(256)`, not a raw E.164 length — the column now carries the same ciphertext envelope Email does, discovered the hard way when `DisclosureHandlerTests` was the first suite to ever seed a phone number through the real protector (Task 19b). `NorseUserClaimsPrincipalFactory` allowlists the resulting principal down to exactly three claims (opaque `Guid` user id, roles, security stamp) — no `ClaimTypes.Name`, since display names now come from the disclosure surface, masked. `ErasureService.ShredAsync` is the three-act crypto-shred ceremony: null the lookup hashes, rotate the security stamp (arming `SecurityStampValidator` to kill live sessions within one revalidation interval — `NorseSignInManager.ValidateSecurityStampAsync` folds the resulting `KeyDestroyedException` to `null` at that one boundary, nowhere else), then destroy the per-subject key via `ISubjectKeyStore.DestroyAsync`, returning an `ErasureReceipt` for the Syn ledger. Payload ciphertext stays in place, dark — this is crypto-shredding, not a content tombstone.

**The disclosure surface is live (Task 19b, same slice).** `Identity.Web.Server/Disclosure/IdentityService` implements Heimdall's `IIdentityService` contract (`Norse.AuthN.Services`, added there in Task 19a alongside `IdentityPolicies` and the four wire records — this repo consumes it via the same `NorseRef` workspace mechanism it already used for `IAuthenticationService`, no new project) with the same bare hydrate-and-send shape as `AuthenticationService`: `GetMyPersonalDataCommand`/`MaskedPersonalDataCommand` wrap the wire requests for mediator identity (`[Authorize(Policy = IdentityPolicies.Self)]`/`.MaskedDisclosure` respectively), and `GetMyPersonalDataHandler`/`GetMaskedPersonalDataHandler` do the actual disclosure: self returns the full decrypted wire strings (subject id from `IPrincipalAccessor`'s principal, resolved by claim-type name via `IOptions<IdentityOptions>.Value.ClaimsIdentity.UserIdClaimType` rather than a hardcoded `ClaimTypes.NameIdentifier` — an absent or non-`Guid` claim fails loudly with `InvalidOperationException` — never from the request, which carries none), masked returns the same two fields through the PII structs' own `IPiiScalar<TSelf>.Parse(...).Masked` law (never hand-masked). Both handlers share one repository fold (spec §3.1): a `KeyDestroyedException` from the value-converter materialization answers `ErrorCategory.Erased` with the receipt intact; a `KeyMissingException` is deliberately left uncaught, falling to `ExceptionTranslationBehavior` as an honest Fault — an incident, never confused with erasure. `IdentityPolicies.Self`/`.MaskedDisclosure` are registered where `AuthNPolicies.Public` already is — the composition root (Yggdrasil), never here; this realm only mirrors the policy name onto its concrete gRPC methods for endpoint metadata, same as `AuthenticationService` already does. **`PersonalData.razor` and its `DownloadPersonalData` endpoint are gone from this repo, not deprecated** — the page ported to Heimdall's `AuthN.Components.FluentUI` in Task 19a (download is now a `GetMyPersonalDataAsync` gRPC call, materialized client-side), and the seam-restored scaffold endpoint in `IdentityComponentsEndpointRouteBuilderExtensions.cs` was deleted outright in the same change that added the real replacement — no deprecation period. `DeletePersonalData.razor` alone stays here; its `UserManager.DeleteAsync` semantics are superseded by the shred ceremony above, and the wire-exposed shred trigger remains a recorded deliberate deferral (spec §7, the Syn DSAR trigger).

**Temporal system-versioning is live, pre-split (2026-08-05).** The "temporal deferred" narrative is over — the marker-and-scaffold adoption of Urðarbrunnr's chassis (`../Glitnir/docs/Platform/specs/2026-08-04-temporal-tables-persistence-chassis-design.md`) landed here squashed into `InitialCreate`, per-provider, and this repo contains **zero hand-written temporal SQL**: the whole adoption is `: ITemporalEntity` on eight entity classes plus a re-issued `dotnet ef migrations add InitialCreate`. `NorseIdentityDbContext` replicates `NorseDbContext`'s plumbing rather than inheriting it, so it also reads `options.GetTemporalRealizationHook()` into a field and passes it as the fourth argument to `NorseModelConventions.Apply` — a four-argument call with no defaults; a three-argument one no longer compiles.

- **Temporal (8), the durable identity and authorization record:** `NorseUser`, `NorseRole`, `NorseUserClaim`, `NorseRoleClaim`, `NorseUserRole`, `NorseUserLogin`, `NorseOpenIddictApplication`, `NorseOpenIddictScope` → tables `users`, `roles`, `user_claims`, `role_claims`, `user_roles`, `user_logins`, `applications`, `scopes` (the OpenIddict tables are named for the entity, not the library — `applications`/`scopes`, never `openiddict_*`). `NorseUserLogin` is in deliberately: a third-party link that existed and was later disconnected is identity record worth keeping.
- **Non-temporal, and this is a ruling (Himinbjörg#47 open question 4, ruled 2026-08-05):** `NorseUserToken` (secret store — superseded TOTP keys and recovery codes must not survive in history), `NorseUserPasskey` (`SignCount` churns every sign-in), `NorseOpenIddictAuthorization` and `NorseOpenIddictToken` (bulk-pruned runtime state; revocation audit is an event-log concern), and `SubjectKey` (crypto-shred law — a temporal `DELETE` would preserve the wrapped DEK in history and make erasure reversible). **Secret material never archives to history.** Both sides of that list are pinned by `NorseIdentityTemporalModelTests`, including a closing fact that no *other* entity carries the stamp — adding or dropping a marker without amending the ruling breaks the build's tests by design.
- **Accepted pre-split rough edge:** the `feature/access-count-breakout` split (Himinbjörg#47) stays parked for .NET 11 preview 7, so lockout churn (`AccessFailedCount`/`LockoutEnd`) still rides the `users` row and a wrong password mints a history row. `TemporalIdentityVersioningTests.A_failed_password_attempt_currently_versions_users` pins that deliberately; the split task **flips** that assertion to #47's exit criterion rather than deleting it. Nothing here composes `IsTemporal()` with `SplitToTable()`, so `dotnet/efcore#30366` is out of reach on this branch and no `TemporalParkedOnSqlServer()` declaration exists yet — the split adds the first one.
- **The one-`InitialCreate`-per-provider law stands** (ruled again 2026-08-05, after a stacked `EnableTemporalIdentity` was built and then thrown away): to change this schema, delete the provider project's `Migrations/` folder and re-add `InitialCreate` — never stack a second migration. Temporal enablement was squashed in exactly that way, so the apparatus emits at table birth through the chassis's `CreateTable` path (spec §3.1), **not** through the §3.3 enable transition — nothing in this repo carries a backfill `UPDATE … SET system_period`. Consequence for tests: never assert on a migration *name*; the container facts assert on the catalog (`pg_class`/`pg_proc`/`pg_trigger`), which survives every squash. The re-issued `InitialCreate` keeps being squashed in place on this branch and is memorialized as the V1 schema only when .NET 11 preview 7's `SplitToTable` fix lands and the shape settles — `users` temporal, `user_lockout` split off and non-temporal.
