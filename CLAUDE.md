## What This Realm Is

Himinbjörg is **the hall behind the gate** — server-only ASP.NET Core Identity + OpenIddict persistence and its gRPC front door. Nothing here crosses to WASM or MAUI; that boundary is load-bearing, not a convenience.

| Project | Carries | Rule |
|---|---|---|
| `Identity.EntityFramework` | The full ASP.NET Core Identity v3 entity set (`NorseUser` … `NorseUserPasskey`), the four `NorseOpenIddict*` entities, `NorseIdentityDbContext` (Identity + OpenIddict via `UseOpenIddict<Guid>()`) | Deliberately `Microsoft.NET.Sdk`, not `Sdk.Web` — the migrations service takes the schema without dragging in the hosting surface |
| `Identity.Web.Server` | `NorseUserStore`/`NorseUserManager`/`NorseSignInManager`/`NorseUserClaimsPrincipalFactory`, the gRPC `AuthenticationService` + `Disclosure/IdentityService`, the command wrappers and handlers, the PII seam (`NorsePersonalDataProtector`/`NorseLookupProtector`/`ErasureService`), and the `/Account` + `/Account/Manage` Razor scaffold still being weaned onto Heimdall page by page | Server-sovereign; consumers call `AddNorseAuthenticationService(connectionStringName)` (`ServiceCollectionExtensions.cs`) and get the whole surface |
| `Identity.Migrations` | `NorseIdentityMigrationContributor` — provider-agnostic, no EF migrations of its own | — |
| `Identity.Migrations.PostgreSQL` / `.SqlServer` | The checked-in per-provider `InitialCreate`, embedded `schema/norse_identity.sql` DDL, and an offline `IDesignTimeDbContextFactory` | One `InitialCreate` per provider, never stacked — see Build & Test |

**Dependency posture:** rides Urðarbrunnr's EF foundation and everything below. NorseRefs Heimdall's `AuthN.Components.FluentUI` (hosting the pages — the `AuthN.Services` contract this realm implements arrives transitively through it, transitive-first by house law, no direct edge) and Asgard's `Abstractions.Web.Server` (mediator law). Two NorseRefs mount source generators (`Generator="true"`): Urðarbrunnr's `Persistence.EntityFramework` and Asgard's `Abstractions.Web.Server` — `AddNorseIdentityWebServerHandlers()` is generated output, never hand-written. Yggdrasil's `Hosting.Web.Server` is the confirmed external consumer. The relationship with Heimdall runs both ways by design: the gate declares, the hall implements and hosts.

**Component placement is a rule, not an inventory** (mirror of Heimdall's law): a page migrates to Heimdall when it is injection-clean of server types; scaffold pages still coupled to `UserManager`/`HttpContext` stay here until ported clean. The `/Account/*` routes are deliberate; renaming is a deferred curation pass.

## Architecture Facts (decided — do not re-litigate)

- **Hydrate-and-send, nothing else:** `AuthenticationService` and `Disclosure/IdentityService` are bare `ISender` forwarders — each method wraps Heimdall's pure wire DTO in a one-line server-sovereign command (`LoginCommand`/`RegisterCommand`/`EmailExistsCommand`/`LogoutCommand`, `GetMyPersonalDataCommand`/`MaskedPersonalDataCommand`; Asgard's `CommandRequest<TRequest,TResponse>`) carrying `[Authorize(Policy = ...)]`. The wire records never carry mediator markers or `[Authorize]` — that's Heimdall law. Handlers answer Asgard's shared shapes directly (`Outcome<NavigationResult>` for issuance — one server-resolved `NextUrl`; `Outcome<BoolResponse>` for the existence check) — no result record exists on either side of the wire. Payload mapping, including the deferred-completion-URL lookup, lives in the handlers.
- **Registration is generated, validators are borrowed:** handlers, Asgard's `CommandRequestValidator<TCommand,TRequest,TResponse>` pass-through adapters (reusing Heimdall's validators unchanged — no hand-written command validator exists), and the dispatch-map entries all come from the generated `AddNorseIdentityWebServerHandlers()`. Never write an `AddScoped` for any of it.
- **Policy names register at Yggdrasil's composition root, never here.** `AuthNPolicies.Public`, `IdentityPolicies.Self`/`.MaskedDisclosure` — this realm only mirrors the names onto its concrete gRPC methods for endpoint metadata. Naming a policy and registering what satisfies it are different jobs.
- **The `Version1`/`Version3` schema gotcha:** ASP.NET Core Identity decides its schema shape (whether the passkey table exists) by reading `IOptions<IdentityOptions>` off the context's `ApplicationServiceProvider`. A caller registering `NorseIdentityDbContext` without the full DI surface — exactly what the migrations service does — would silently get `Version1` and lose the passkey table. `NorseIdentityDbContext.OnConfiguring` carries a fallback `IServiceProvider` forcing `Version3` for that path; read the type's doc comment before "fixing" it away.
- **`EmailExistsHandler` resolves a fresh DI scope per call — load-bearing, not style.** Blazor Server resolves all circuit services from one scope, and the register validator's email rule fires on blur AND again on submit without awaiting the first; two overlapping calls on the circuit's single `DbContext` throw `A second operation was started on this context instance` — reproduced live.
- **`LoginHandler`'s anti-enumeration collapse is a reference-identity guarantee** (spec §9.3): every credential-failure path returns the same static `Failed` instance — `Problem.Errors` is a dictionary, so two separately built Problems compare unequal as records; the collapse is provable by reference. `PathBase` is read per-`Handle` so `NextUrl` values survive non-root hosting.
- **Deferred sign-in:** `NorseSignInManager` signs in/out normally while the response can still write a cookie, otherwise stashes via `IDeferredSignIn` and records the completion key on `DeferredSignInKeyItemName`; a forced full-page navigation to the completion endpoint finishes it on a genuine new request. `ValidateSecurityStampAsync` folds `KeyDestroyedException` to `null` at that one boundary — nowhere else.
- **The PII seam:** `NorsePersonalDataProtector` envelope-encrypts (`v1:{subjectId:D}:{base64(nonce ∥ ciphertext ∥ tag)}`, AES-256-GCM) every `[ProtectedPersonalData]` column, keyed per subject through Asgard's `ISubjectKeyStore` via the ambient `SubjectCryptoScope` that `NorseUserManager.CreateAsync`/`UpdateUserAsync` establish around the base call — every write path must flow through them. `NorseLookupProtector` backs the HMAC blind-index columns (`NormalizedEmail`/`NormalizedUserName`) so lookups never compare plaintext. `NorseUser.PhoneNumber` is `character varying(256)` because it carries the ciphertext envelope, not an E.164 string — discovered the hard way. The principal is allowlisted to exactly three claims (opaque `Guid` id, roles, security stamp) — no `ClaimTypes.Name`; display names come from the disclosure surface, masked.
- **Crypto-shred, not tombstone:** `ErasureService.ShredAsync` is three acts — null the lookup hashes, rotate the security stamp (live sessions die within one revalidation interval), destroy the per-subject key — returning an `ErasureReceipt`. Ciphertext stays in place, permanently dark. A `KeyDestroyedException` surfacing from EF materialization answers `ErrorCategory.Erased` with the receipt intact; a `KeyMissingException` deliberately falls through as an honest Fault — an incident, never confused with erasure.
- **Disclosure is shaped by unrepresentability:** the subject id comes from the principal (via `IOptions<IdentityOptions>.Value.ClaimsIdentity.UserIdClaimType`, never a hardcoded claim type, never the request — absent or non-`Guid` fails loudly); masked disclosure goes through the PII structs' own `IPiiScalar<TSelf>.Parse(...).Masked`, never hand-masked. `PersonalData.razor` and the JSON-download endpoint are **gone from this repo, not deprecated** — ported to Heimdall as a gRPC call. `DeletePersonalData.razor` stays; its `DeleteAsync` semantics are superseded by the shred ceremony, and the wire-exposed shred trigger is a recorded deliberate deferral (PII spec §7, the Syn DSAR trigger).
- **Temporal (8), the durable identity and authorization record:** `NorseUser`, `NorseRole`, `NorseUserClaim`, `NorseRoleClaim`, `NorseUserRole`, `NorseUserLogin`, `NorseOpenIddictApplication`, `NorseOpenIddictScope` → tables `users`, `roles`, `user_claims`, `role_claims`, `user_roles`, `user_logins`, `applications`, `scopes` (OpenIddict tables are named for the entity, never `openiddict_*`). `NorseUserLogin` is in deliberately — a disconnected third-party link is identity record worth keeping. Zero hand-written temporal SQL exists here: the whole adoption is `: ITemporalEntity` plus a re-issued `InitialCreate`.
- **Non-temporal, and this is a ruling (Himinbjörg#47 Q4, 2026-08-05):** `NorseUserToken` (superseded secrets must not survive in history), `NorseUserPasskey` (`SignCount` churn), `NorseOpenIddictAuthorization`/`NorseOpenIddictToken` (bulk-pruned runtime state), `SubjectKey` (a temporal `DELETE` would preserve the wrapped DEK and make crypto-shredding reversible). **Secret material never archives to history.** Both sides are pinned by `NorseIdentityTemporalModelTests`, including a closing fact that no other entity carries the stamp — changing a marker without amending the ruling breaks tests by design.
- **Accepted pre-split rough edge:** lockout churn (`AccessFailedCount`/`LockoutEnd`) still rides `users`, so a wrong password mints a history row. `TemporalIdentityVersioningTests.A_failed_password_attempt_currently_versions_users` pins that deliberately; the parked `feature/access-count-breakout` split (waiting on .NET 11 preview 7) **flips** that assertion to #47's exit criterion rather than deleting it.
- **Never assert on a migration name** — the `InitialCreate` squash cycle would break it. Container facts assert on the catalog (`pg_class`/`pg_proc`/`pg_trigger`), which survives every squash.
- **`NorseIdentityDbContext` replicates `NorseDbContext`'s plumbing rather than inheriting it** — it reads `options.GetTemporalRealizationHook()` into a field and passes it as the fourth argument to `NorseModelConventions.Apply`; a three-argument call no longer compiles.
