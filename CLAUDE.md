## What This Realm Is

Himinbjörg is **the hall behind the gate** — server-only ASP.NET Core Identity + OpenIddict persistence and its gRPC front door. Nothing here crosses to WASM or MAUI; that boundary is load-bearing, not a convenience.

| Project | Carries | Rule |
|---|---|---|

**Component placement is a rule, not an inventory** (mirror of Heimdall's law): a page migrates to Heimdall when it is injection-clean of server types; scaffold pages still coupled to `UserManager`/`HttpContext` stay here until ported clean. The anonymous tier is on gRPC: the nine scaffold pages it replaced (`ForgotPassword`, `ResetPassword`, `LoginWith2fa`, `LoginWithRecoveryCode`, `ConfirmEmail`, `ConfirmEmailChange`, `ResendEmailConfirmation`, `RegisterConfirmation`, `InvalidUser`) are deleted, and `ScaffoldRetirementTests` keeps their routes out of this assembly, since Heimdall owns them and a duplicate template throws in Yggdrasil's router. The account core is on gRPC too: the six Manage pages it replaced (`Index`, `Email`, `ChangePassword`, `SetPassword`, `ExternalLogins`, `DeletePersonalData`) are deleted and pinned by the same test. What survives is the two-factor and passkey pages under `/Account/Manage` and the external-login callback. The second factor rides an opaque, data-protected challenge token (`TwoFactorChallenge`), never the partial two-factor cookie; Blazor-Server sign-ins that cannot Set-Cookie finish through `DeferredCompletion`; recovery-code replacement goes through `IRecoveryCodeReplacement`, which keeps the commit outcome that `GenerateNewTwoFactorRecoveryCodesAsync` loses. The `/Account/*` routes are deliberate; renaming is a deferred curation pass.

## Architecture Facts (decided — do not re-litigate)

- **Hydrate-and-send, nothing else:** `AuthenticationService`, `Disclosure/IdentityService` and `Account/AccountService` are bare `ISender` forwarders — each method wraps Heimdall's pure wire DTO in a one-line server-sovereign command (the original `LoginCommand`/`RegisterCommand`/`EmailExistsCommand`/`LogoutCommand`, the anonymous tier's `TwoFactorSignInCommand`/`RecoveryCodeSignInCommand`/`ForgotPasswordCommand`/`ResetPasswordCommand`/`ConfirmEmailCommand`/`ConfirmEmailChangeCommand`/`ResendEmailConfirmationCommand`, disclosure's `GetMyPersonalDataCommand`/`MaskedPersonalDataCommand`, and the account core's `GetAccountStatusCommand`/`SetPhoneNumberCommand`/`ChangeEmailCommand`/`ChangePasswordCommand`/`SetPasswordCommand`/`GetExternalLoginsCommand`/`RemoveExternalLoginCommand`/`DeletePersonalDataCommand`; Asgard's `CommandRequest<TRequest,TResponse>`) carrying `[Authorize(Policy = ...)]`. The wire records never carry mediator markers or `[Authorize]` — that's Heimdall law. Handlers answer Asgard's shared shapes directly (`Outcome<NavigationResult>` for sign-in, sign-out and every other navigating answer — one server-resolved `NextUrl`; `Outcome<BoolResponse>` for the existence check and the acknowledgments) — no result record exists on either side of the wire. Payload mapping, including the deferred-completion-URL lookup, lives in the handlers.
- **Registration is generated, validators are borrowed:** handlers, Asgard's `CommandRequestValidator<TCommand,TRequest,TResponse>` pass-through adapters (reusing Heimdall's validators unchanged — no hand-written command validator exists), and the dispatch-map entries all come from the generated `AddNorseIdentityWebServerHandlers()`. Never write an `AddScoped` for any of it.
- **Policy names register at Yggdrasil's composition root, never here.** `AuthNPolicies.Public`/`.Account`, `IdentityPolicies.Self`/`.MaskedDisclosure` — this realm only mirrors the names onto its concrete gRPC methods for endpoint metadata. Naming a policy and registering what satisfies it are different jobs.
- **The `Version1`/`Version3` schema gotcha:** ASP.NET Core Identity decides its schema shape (whether the passkey table exists) by reading `IOptions<IdentityOptions>` off the context's `ApplicationServiceProvider`. A caller registering `NorseIdentityDbContext` without the full DI surface — exactly what the migrations service does — would silently get `Version1` and lose the passkey table. `NorseIdentityDbContext.OnConfiguring` carries a fallback `IServiceProvider` forcing `Version3` for that path; read the type's doc comment before "fixing" it away.
- **`EmailExistsHandler` resolves a fresh DI scope per call — load-bearing, not style.** Blazor Server resolves all circuit services from one scope, and the register validator's email rule fires on blur AND again on submit without awaiting the first; two overlapping calls on the circuit's single `DbContext` throw `A second operation was started on this context instance` — reproduced live.
- **`LoginHandler`'s anti-enumeration collapse is a reference-identity guarantee** (spec §9.3): every credential-failure path returns the same static `Failed` instance — `Problem.Errors` is a dictionary, so two separately built Problems compare unequal as records; the collapse is provable by reference. `PathBase` is read per-`Handle` so `NextUrl` values survive non-root hosting.
- **Deferred sign-in:** `NorseSignInManager` signs in/out normally while the response can still write a cookie, otherwise stashes via `IDeferredSignIn` and records the completion key on `DeferredSignInKeyItemName`; a forced full-page navigation to the completion endpoint finishes it on a genuine new request.
- **The PII seam:** `NorsePersonalDataProtector` envelope-encrypts (`v1:{subjectId:D}:{base64(nonce ∥ ciphertext ∥ tag)}`, AES-256-GCM) every `[ProtectedPersonalData]` column, keyed per subject through Asgard's `ISubjectKeyStore` via the ambient `SubjectCryptoScope` that `NorseUserManager.CreateAsync`/`UpdateUserAsync`/`RedeemTwoFactorRecoveryCodeAsync` establish around the base call — every write path must flow through them. `NorseLookupProtector` backs the HMAC blind-index columns (`NormalizedEmail`/`NormalizedUserName`) so lookups never compare plaintext. `NorseUser.PhoneNumber` is `character varying(256)` because it carries the ciphertext envelope, not an E.164 string — discovered the hard way. The principal is allowlisted to exactly three claims (opaque `Guid` id, roles, security stamp) — no `ClaimTypes.Name`; display names come from the disclosure surface, masked.
- **Erasure is a hard delete, key first** (`Himinbjorg/specs/2026-10-24-identity-explicit-writes-temporal-split-design.md` §7, superseding the darken-in-place ceremony): `ErasureService.ShredAsync` probes the key, destroys it unconditionally unless `Missing` (linearizable per subject, one authoritative receipt), then in one transaction deletes the subject's OpenIddict tokens and authorizations and the `users` row through a raw `DELETE` (`ExecuteDelete` refuses a split entity; the cascade takes every child table). Every step is idempotent and every `Ok` run does every step, so retry-until-`Ok` finishes any partial failure; infrastructure failures (lock exhaustion, key-store I/O, database) answer `Fault`, `Missing` with no row answers `NotFound`, `Missing` with a row answers `Fault` (an incident), and a lost commit acknowledgement answers `Indeterminate`, never `Fault` (the deletes may have landed; the re-run is safe either way). It is the **only** door that removes a user: `NorseUserStore.DeleteAsync` throws `NotSupportedException` naming `ShredAsync`. Between destruction and commit, materialization throws `KeyDestroyedException`, which disclosure answers as `Erased` with the receipt; once the row is gone a live lookup answers `NotFound` (§7.4 interim). Live sessions die at the next revalidation because the user is gone.
- **Disclosure is shaped by unrepresentability:** the subject id comes from the principal (via `IOptions<IdentityOptions>.Value.ClaimsIdentity.UserIdClaimType`, never a hardcoded claim type, never the request — absent or non-`Guid` fails loudly); masked disclosure goes through the PII structs' own `IPiiScalar<TSelf>.Parse(...).Masked`, never hand-masked. `PersonalData.razor` and the JSON-download endpoint are **gone from this repo, not deprecated** — ported to Heimdall as a gRPC call. `DeletePersonalData.razor` is gone the same way: self-erasure is `AccountService` → `DeletePersonalDataHandler`, which gates on the password (a passwordless account skips the check; a wrong password answers one static `InvalidCredentials` instance and shreds nothing), shreds through `ErasureService.ShredWithRetriesAsync` (3 attempts, since past the key's destruction the caller has no second request to retry from), and signs out only after the shred succeeds. The operator-side shred trigger stays a recorded deliberate deferral (PII spec §7, the Syn DSAR trigger).
- **Temporal (7), the durable identity and authorization record:** `NorseUser` (its `users` principal only), `NorseRole`, `NorseUserClaim`, `NorseRoleClaim`, `NorseUserRole`, `NorseOpenIddictApplication`, `NorseOpenIddictScope` → tables `users`, `roles`, `user_claims`, `role_claims`, `user_roles`, `applications`, `scopes` (OpenIddict tables are named for the entity, never `openiddict_*`). Zero hand-written temporal SQL exists here: the adoption is `: ITemporalEntity` plus a re-issued `InitialCreate`. `NorseUser` is a split entity, so it also declares Urðarbrunnr's `TemporalOnPrincipalTableOnly()`: SQL Server versions `Users` engine-natively with hidden periods and gives the fragment nothing (no `TemporalAsOf`/`TemporalAll` on `NorseUser` there, accepted for Identity only); on PostgreSQL the opt-in is a no-op. `user_claims` stays temporal under the rule that claim values never carry PII.
- **Non-temporal, and this is a ruling (Himinbjörg#47 Q4, 2026-08-05; amended by the 2026-10-24 spec):** `user_credentials` (the `NorseUser` fragment: `PasswordHash`, `SecurityStamp`, `AccessFailedCount`, `LockoutEnd` and the two HMAC blind indexes — credential, lookup and rate-limiter churn, and *anything computed under a platform key never enters history*), `NorseUserLogin` (`provider_key` is a plaintext third-party subject id forming the primary key, so it can't be encrypted or blind-indexed out of history; link/unlink history moves to receipts, #55), `NorseUserToken` (superseded secrets must not survive in history), `NorseUserPasskey` (`SignCount` churn), `NorseOpenIddictAuthorization`/`NorseOpenIddictToken` (bulk-pruned runtime state), `SubjectKey` (a temporal `DELETE` would preserve the wrapped DEK and make crypto-shredding reversible). **Secret material never archives to history.** Both sides are pinned by `NorseIdentityTemporalModelTests`, including a closing fact that no other entity carries the stamp — changing a marker without amending the ruling breaks tests by design — and on the live catalog by `NorseIdentityTemporalApparatusContainerTests` (PostgreSQL) and `SqlServerIdentitySchemaTests`.
- **Lockout and credential churn ride `user_credentials`, never `users`:** a wrong password, a password change, a stamp rotation and a lockout each write zero `users_history` rows. `Failed_password_writes_no_users_history` pins it on both providers (it replaced the pre-split `A_failed_password_attempt_currently_versions_users`); `LockoutEnabled` stays on `users`, because it is admin policy and so identity record.
- **Email is the username, enforced by the database:** both blind indexes are `NOT NULL` and `user_credentials` carries `CHECK (normalized_email = normalized_user_name)`. EF can't declare a CHECK on a split-table fragment, so it is declared through Urðarbrunnr's `HasFragmentCheckConstraint` seam, which both providers' migrations generators emit on the fragment table. The unique index on `normalized_user_name` therefore *is* email uniqueness. `RequireUniqueEmail = true` on the production registration path makes Identity's own validator refuse an email-less user (`InvalidEmail`) before any write. `NorseUserManager.SetEmailAsync`/`ChangeEmailAsync` set `Email`, `UserName`, both hashes and the stamp in one flush (one `users` version), and translate the store's `DuplicateUserName` into `DuplicateEmail`; `SetUserNameAsync` is refused with `UserNameIsDerived` (`NorseUserManager.UserNameIsDerivedErrorCode`) and writes nothing.
- **`NorseUserStore` implements the `IUser*Store` interfaces directly — no `UserStore<…>` base, no change tracker** (platform NoTracking stays law). Every `FindBy*` reads the whole entity untracked and registers a per-instance as-read baseline (a static `ConditionalWeakTable`, not an identity map); an instance without one is refused by `UpdateAsync`. Mutating store calls stage typed intents; `UpdateAsync` diffs plaintext against the baseline and flushes explicit statements — the `users` update guarded by `concurrency_stamp`, the `user_credentials` CAS, one statement per child intent (savepoints around login and passkey inserts) — in one transaction under a zero-retry strategy (`ZeroRetryExecutionStrategy`; never blind replay). Unchanged columns never appear in a `SET`, and an empty diff touches nothing. A definite failure leaves the instance exactly as read. The immediate operations — the access-failed increment and recovery-code redemption — are raw single statements, each in its own committed transaction, never staged and never repeated. The commit-outcome contract is definite vs `Indeterminate` (`Store/CommitBoundary.cs`): a failed commit is resolved by the stamp marker, by a rollback probe on SQL Server or by `pg_xact_status` on PostgreSQL; what can't be resolved answers `IndeterminateOutcome` (or throws `IndeterminateWriteException` from the immediate operations) and poisons the instance until re-read. `DeleteAsync` is refused in favor of `ShredAsync`, `GetUsersForClaimAsync`/`GetUsersInRoleAsync` are refused (subject-singular law), and `IQueryableUserStore` is not implemented.
- **Norse callers see `Outcome<T>`, never `IdentityResult`, `SignInResult` or OpenIddict exceptions.** Every handler, service and endpoint goes through a `.Outcome` view (`userManager.Outcome.ChangeEmailAsync(…)`), with one mapping table in `IdentityOutcomeMap` (every pinned `IdentityErrorDescriber` code mapped explicitly, unmapped → `Fault`, `IndeterminateOutcome` → `Indeterminate`, `KeyDestroyedException` → `Erased`). `No_handler_service_or_endpoint_calls_raw_Identity_or_OpenIddict_manager_methods` (an IL scan) enforces it; `Components/` is exempt until #48 retires the scaffold. The managers themselves stay stock. **Framework-boundary adapters stay where they are:** `NorseSignInManager.ValidateSecurityStampAsync` folds a destroyed key to `null` and `IdentityRevalidatingAuthenticationStateProvider` folds it to "invalid", both classifying through `IdentityOutcomeMap.IsErased` — the framework calls them directly, never through `.Outcome`.
- **No token-bearing log line outside `Development`.** A reset link, a reset code and a confirmation link are credentials, and Midgard's service defaults export formatted logs through OpenTelemetry. `AddNorseAuthenticationService` resolves `IEmailSender<NorseUser>` per environment: `DevelopmentEmailSender` (logs each link and code verbatim, by design) under `Development` only, the silent `IdentityNoOpEmailSender` everywhere else. A host wiring a real sender registers its own afterward and wins. `ServiceCollectionExtensionsTests` enforces it (`Outside_Development_nothing_token_bearing_is_logged`).
- **The last sign-in method is guarded under the row lock** (account-lifecycle spec §5.9): `FlushExecutor`'s `RemoveLogin` arm reads the password under a `FOR UPDATE` / `UPDLOCK, HOLDLOCK` lock on the user's `user_credentials` row, counts the logins that would *remain*, and refuses a removal that would leave neither a password nor a login with `LastSignInMethod` → `Conflict`; removing a login the user doesn't have leaves the count unchanged, so it stays a no-op. On the manager path the stamp CAS already serializes stale instances; the lock serializes any flush the CAS doesn't cover, so the count is authoritative. The page hiding the button is not the guard — the wire doesn't hide it. `LastSignInMethodSuite` pins it on both providers.
- **The external-login link pair is the only Manage HTTP surface:** `GET /Account/Manage/LinkExternalLogin?provider=` (an unknown provider challenges nothing and redirects with `external-login-not-added`) and `GET /Account/Manage/LinkExternalLoginCallback`; the manage group requires `AuthNPolicies.Account`. The provider's return leg has no gRPC answer, so the outcome rides the redirect to `/Account/Manage/ExternalLogins`: `?status=external-login-added` on success, `?status=external-login-not-added` on a definite failure, and no status key on an `Indeterminate` link, so the page lists the truth on load. The callback clears the external cookie on every exit.
- **Never assert on a migration name** — the `InitialCreate` squash cycle would break it. Container facts assert on the catalog (`pg_class`/`pg_proc`/`pg_trigger`), which survives every squash.
- **`NorseIdentityDbContext` replicates `NorseDbContext`'s plumbing rather than inheriting it** — it reads `options.GetTemporalRealizationHook()` into a field and passes it as the fourth argument to `NorseModelConventions.Apply`; a three-argument call no longer compiles.
