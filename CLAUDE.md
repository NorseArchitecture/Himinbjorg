## What This Realm Is

Himinbjörg is **the hall behind the gate** — server-only ASP.NET Core Identity + OpenIddict persistence and its gRPC front door. Nothing here crosses to WASM or MAUI; that boundary is load-bearing, not a convenience.

## Architecture Facts (decided — do not re-litigate)

- **Hydrate-and-send, nothing else:** `AuthenticationService`, `Disclosure/IdentityService`, `Account/AccountService` and Train 3's three services are bare `ISender` forwarders — each method wraps Heimdall's pure wire DTO in a one-line server-sovereign command (the original `LoginCommand`/`RegisterCommand`/`EmailExistsCommand`/`LogoutCommand`, the anonymous tier's `TwoFactorSignInCommand`/`RecoveryCodeSignInCommand`/`ForgotPasswordCommand`/`ResetPasswordCommand`/`ConfirmEmailCommand`/`ConfirmEmailChangeCommand`/`ResendEmailConfirmationCommand`, disclosure's `GetMyPersonalDataCommand`/`MaskedPersonalDataCommand`, and the account core's `GetAccountStatusCommand` (behind `AuthNPolicies.AccountRead`)/`SetPhoneNumberCommand`/`ChangeEmailCommand`/`ChangePasswordCommand`/`SetPasswordCommand`/`GetExternalLoginsCommand`/`RemoveExternalLoginCommand`/`DeletePersonalDataCommand`, and Train 3's `TwoFactor/TwoFactorService` (`GetAuthenticatorSetupCommand`/`EnableAuthenticatorCommand`/`ResetAuthenticatorCommand`/`DisableTwoFactorCommand`/`ForgetTwoFactorClientCommand`/`GenerateRecoveryCodesCommand`/`RevealRecoveryCodesCommand`) and `Passkeys/PasskeyService` (`GetPasskeysCommand`/`GetPasskeyCommand`/`GetPasskeyCreationOptionsCommand`/`AddPasskeyCommand`/`RenamePasskeyCommand`/`RemovePasskeyCommand`), both behind `AuthNPolicies.Account`, and `SignInMethods/SignInMethodsService` (`GetSignInMethodsCommand`/`GetPasskeyRequestOptionsCommand`/`PasskeySignInCommand`) behind `AuthNPolicies.Public`; Asgard's `CommandRequest<TRequest,TResponse>`) carrying `[Authorize(Policy = ...)]`. The wire records never carry mediator markers or `[Authorize]` — that's Heimdall law. Handlers answer Asgard's shared shapes directly (`Outcome<NavigationResult>` for sign-in, sign-out and every other navigating answer — one server-resolved `NextUrl`; `Outcome<BoolResponse>` for the existence check and the acknowledgments) — no result record exists on either side of the wire. Payload mapping, including the deferred-completion-URL lookup, lives in the handlers.
- **Registration is generated, validators are borrowed:** handlers, Asgard's `CommandRequestValidator<TCommand,TRequest,TResponse>` pass-through adapters (reusing Heimdall's validators unchanged — no hand-written command validator exists), and the dispatch-map entries all come from the generated `AddNorseIdentityWebServerHandlers()`. Never write an `AddScoped` for any of it.
- **Policy names register at Yggdrasil's composition root, never here.** `AuthNPolicies.Public`/`.Account`/`.AccountRead`, `IdentityPolicies.Self`/`.MaskedDisclosure`, `NorsePolicies.RecentAuthentication` — this realm only mirrors the operation policies onto its concrete gRPC methods for endpoint metadata. Naming a policy and registering what satisfies it are different jobs.
- **Freshness rides the command, lanes ride the policy** (OpenIddict step-up spec §6.3, §7.5; T4-3, T4-4, PF7). The four step-up operations' five commands (`GetPasskeyCreationOptions`/`AddPasskey` → `/Account/Manage/Passkeys`, `DisableTwoFactor` → `/Account/Manage/Disable2fa`, `GetAuthenticatorSetup` → `/Account/Manage/EnableAuthenticator`, `ResetAuthenticator` → `/Account/Manage/ResetAuthenticator`) carry a second `[Authorize(Policy = NorsePolicies.RecentAuthentication)]` beside `Account`, and `[ReauthenticationLanding]`. The gRPC methods mirror only the operation policy, never freshness, and no service carries a class-level `[Authorize]`: an endpoint-edge freshness check would refuse a stale caller with a bare 403 before Midgard's mediator could answer `Forbidden` with `reauthentication-required` and `NextUrl = PathBase/Account/Login?returnUrl=PathBase+landing` (evaluated last, only for a caller every operation policy admits; every other refusal stays bare). The link start `GET /Account/Manage/LinkExternalLogin` is the HTTP twin: it declares its landing (`/Account/Manage/ExternalLogins`) as endpoint metadata, and an endpoint filter, after the group's `Account` policy, evaluates freshness and redirects a stale caller (the failure reason whose message is `reauthentication-required`) to the same URL shape, built exactly as Midgard builds it (PF4); never `RequireAuthorization`, which would fold freshness into the account policy and answer a bare 403. The callback is not gated. `GetAccountStatus` is `AuthNPolicies.AccountRead` alone (the cookie, or a user bearer with `aud = Norse.User`), as is disclosure's `Self`; every `Account` and `Public` operation admits only the `Identity` lane (the generated policy registration closes every lane-silent policy to it), so a user bearer, alone or beside a valid cookie (the bearer decides), is refused by all of them (`ForgotPassword` sends nothing), and a machine token by every user-facing policy. `CommandPolicyTests` pins the attributes, `FreshnessSuite` and `LaneAdmissionSuite` the behavior over the real gRPC pipeline on both providers (`GrpcSurfaceHost`).
- **`Norse.Bearer` is this realm's, registered by `AddNorseAuthenticationService`** (spec §7.1, Task 4.1): Midgard's `Norse.Machine` and `Norse.User` lanes authenticate it by name and stamp the lane; it forwards to the one OpenIddict validation scheme, which accepts both audiences (`Norse.Facade`, `Norse.User`), through `OpenIddict/BearerChallengeHandler`, which authenticates before it challenges (OpenIddict's challenge otherwise answers ID2095's 403 to a request that never authenticated, re-verified on 8.0.0-preview.4), so every bearer refusal is a bare 401 or 403. A challenge after the bearer itself succeeded is a lane refusing the validated token (Buvy's lane ruling, Midgard's audience check: `Norse.Machine` needs exactly `Norse.Facade`, `Norse.User` exactly `Norse.User`), an authentication failure, which OpenIddict would answer as the authenticated request it saw (403 `insufficient_access`); so the challenge names `invalid_token` unless the caller named an error, and a wrong-kind token on either lane is the bare 401 (`WWW-Authenticate: Bearer error="invalid_token"`, no description or URI). `BearerSchemeTests` pins it, and `LaneAdmissionSuite` pins the composed shape on both lanes.
- **The `Version1`/`Version3` schema gotcha:** ASP.NET Core Identity decides its schema shape (whether the passkey table exists) by reading `IOptions<IdentityOptions>` off the context's `ApplicationServiceProvider`. A caller registering `NorseIdentityDbContext` without the full DI surface — exactly what the migrations service does — would silently get `Version1` and lose the passkey table. `NorseIdentityDbContext.OnConfiguring` carries a fallback `IServiceProvider` forcing `Version3` for that path; read the type's doc comment before "fixing" it away.
- **`EmailExistsHandler` resolves a fresh DI scope per call — load-bearing, not style.** Blazor Server resolves all circuit services from one scope, and the register validator's email rule fires on blur AND again on submit without awaiting the first; two overlapping calls on the circuit's single `DbContext` throw `A second operation was started on this context instance` — reproduced live.
- **`LoginHandler`'s anti-enumeration collapse is a reference-identity guarantee** (spec §9.3): every credential-failure path returns the same static `Failed` instance — `Problem.Errors` is a dictionary, so two separately built Problems compare unequal as records; the collapse is provable by reference. `PathBase` is read per-`Handle` so `NextUrl` values survive non-root hosting.
- **Deferred sign-in:** `NorseSignInManager` signs in/out normally while the response can still write a cookie, otherwise stashes via `IDeferredSignIn` and records the completion key on `DeferredSignInKeyItemName`; a forced full-page navigation to the completion endpoint finishes it on a genuine new request.
- **The PII seam:** `NorsePersonalDataProtector` envelope-encrypts (`v1:{subjectId:D}:{base64(nonce ∥ ciphertext ∥ tag)}`, AES-256-GCM) every `[ProtectedPersonalData]` column, keyed per subject through Asgard's `ISubjectKeyStore` via the ambient `SubjectCryptoScope` that `NorseUserManager.CreateAsync`/`UpdateUserAsync`/`RedeemTwoFactorRecoveryCodeAsync` establish around the base call — every write path must flow through them. `NorseLookupProtector` backs the HMAC blind-index columns (`NormalizedEmail`/`NormalizedUserName`) so lookups never compare plaintext. `NorseUser.PhoneNumber` is `character varying(256)` because it carries the ciphertext envelope, not an E.164 string — discovered the hard way. The cookie principal is allowlisted to four persistent claims plus one transient (OpenIddict step-up spec §6.1): `NorseUserClaimsPrincipalFactory` keeps exactly the opaque `Guid` id (`ClaimTypes.NameIdentifier`), roles (`ClaimTypes.Role`) and the security stamp (`AspNet.Identity.SecurityStamp`), and `NorseSignInManager`'s stamp point adds `auth_time` (`NorseClaimTypes.AuthTime`, integral epoch seconds, `Integer64`); the transient `norse_reauth` binding is stamped only on a credential sign-in whose landing carries a valid marker, never carried by a refresh or the stamp validator, and never enters a token. **The binding reads one slot** (T4-1): the stamp point takes the landing only from `ReauthLandingItemName`, filled in exactly two places, each removing it in a `finally` — `SignInOrTwoFactorAsync`'s direct branch (password without a second factor, passkey) copies the `ParkedReturnUrl` landing, and the two-factor completion (authenticator, recovery code, external login) sets `ReturnUrls.Resolve(challenge.ReturnUrl)` before its sign-in and still returns the challenge's landing unchanged; any other `SignInWithClaimsAsync` (registration's included) binds nothing. It stamps `norse_reauth` = the marker id (`"N"`) only at refresh depth 0, only when the landing's path is exactly `PathBase + /connect/authorize` (ordinal), its query carries exactly one parameter named exactly `norse_reauth` (ordinal, as the hash excludes it: `NORSE_REAUTH` is an unknown parameter that stamps nothing and takes part in the hash; two exact ones stamp nothing), and that value unprotects through `OpenIddict/ReauthMarkers` (purpose `Norse.Identity.ReauthMarker.v1`, base64url, expiry inside the payload judged by the injected `TimeProvider`, `Lifetime` 5 minutes) naming this user or no user (an anonymous challenge binds whoever presents the credential). The marker carries `OpenIddict/AuthorizeTransaction.Hash` (T4-10: SHA-256 over the parameter count, then per ordinal-sorted name a `0x01` tag, length-prefixed UTF-8 name and value count, then each value as a `0x02` tag and length-prefixed UTF-8 value, `int32` little-endian, `norse_reauth` excluded; a known-answer fact pins the bytes). `ReauthBindingTests` is gate H5: all five credential paths, immediate and deferred through Midgard's real `/_auth/complete`, bind the cookie the browser ends up holding. No `ClaimTypes.Name`; display names come from the disclosure surface, masked. The only other claims a cookie carries are ASP.NET Core Identity's own sign-in-method markers (`amr`: `pwd`, or `mfa` after a second factor; `ClaimTypes.AuthenticationMethod` for an external provider), and `AuthTimeSuite` pins a password sign-in's whole set exactly on both providers. **`auth_time` is stamped only by credential presentation** (T4-2): every `SignInWithClaimsAsync` is a credential sign-in (password, two-factor completion, recovery code, passkey, external login, registration's sign-in) and stamps `TimeProvider.GetUtcNow()`, except inside `RefreshSignInAsync`, whose override counts a refresh depth around the base call (restored in a `finally`) so the stamp point carries the ticket's value instead — exactly one, or none, so a pre-train cookie stays stale. `SecurityStampValidatorOptions.OnRefreshingPrincipal` carries it the same way. Neither ever reads `HttpContext.User` (Midgard's lane-stamped rebuild): `No_type_that_signs_a_principal_in_reads_an_ambient_principal` pins it (no signer reads `HttpContext.User`, `AuthenticationStateProvider`, a schemeless `AuthenticateAsync` or one that never names the Identity cookie's scheme, or a minimal-API `ClaimsPrincipal` parameter; canaries in `PrincipalSourceCanaries/` prove each is caught), and the IL scan bans `SignInManager.IsSignedIn`, which matches `Identity.Application` by `AuthenticationType` and so answers false for every lane-stamped principal.
- **Erasure is a hard delete, key first** (`Himinbjorg/specs/2026-10-24-identity-explicit-writes-temporal-split-design.md` §7, superseding the darken-in-place ceremony): `ErasureService.ShredAsync` probes the key, destroys it unconditionally unless `Missing` (linearizable per subject, one authoritative receipt), then in one transaction deletes the subject's OpenIddict rows in foreign-key order, since none of their keys cascades (tokens by subject, authorization or session; then sessions by subject or authorization; then authorizations by subject; OpenIddict step-up spec §5.5, `An_erased_subjects_sessions_are_gone`), and the `users` row through a raw `DELETE` (`ExecuteDelete` refuses a split entity; the cascade takes every child table). Every step is idempotent and every `Ok` run does every step, so retry-until-`Ok` finishes any partial failure; infrastructure failures (lock exhaustion, key-store I/O, database) answer `Fault`, `Missing` with no row answers `NotFound`, `Missing` with a row answers `Fault` (an incident), and a lost commit acknowledgement answers `Indeterminate`, never `Fault` (the deletes may have landed; the re-run is safe either way). It is the **only** door that removes a user: `NorseUserStore.DeleteAsync` throws `NotSupportedException` naming `ShredAsync`. Between destruction and commit, materialization throws `KeyDestroyedException`, which disclosure answers as `Erased` with the receipt; once the row is gone a live lookup answers `NotFound` (§7.4 interim). Live sessions die at the next revalidation because the user is gone.
- **Disclosure is shaped by unrepresentability:** the subject id comes from the principal (via `IOptions<IdentityOptions>.Value.ClaimsIdentity.UserIdClaimType`, never a hardcoded claim type, never the request — absent or non-`Guid` fails loudly); masked disclosure goes through the PII structs' own `IPiiScalar<TSelf>.Parse(...).Masked`, never hand-masked. `PersonalData.razor` and the JSON-download endpoint are **gone from this repo, not deprecated** — ported to Heimdall as a gRPC call. `DeletePersonalData.razor` is gone the same way: self-erasure is `AccountService` → `DeletePersonalDataHandler`, which gates on the password (a passwordless account skips the check; a wrong password answers one static `InvalidCredentials` instance and shreds nothing), shreds through `ErasureService.ShredWithRetriesAsync` (3 attempts, since past the key's destruction the caller has no second request to retry from), and signs out only after the shred succeeds. The operator-side shred trigger stays a recorded deliberate deferral (PII spec §7, the Syn DSAR trigger).
- **Temporal (8), the durable identity and authorization record:** `NorseUser` (its `users` principal only), `NorseRole`, `NorseUserClaim`, `NorseRoleClaim`, `NorseUserRole`, `NorseOpenIddictApplication`, `NorseOpenIddictScope`, `NorseOpenIddictResource` → tables `users`, `roles`, `user_claims`, `role_claims`, `user_roles`, `applications`, `scopes`, `resources` (OpenIddict tables are named for the entity, never `openiddict_*`). Zero hand-written temporal SQL exists here: the adoption is `: ITemporalEntity` plus a re-issued `InitialCreate`. `NorseUser` is a split entity, so it also declares Urðarbrunnr's `TemporalOnPrincipalTableOnly()`: SQL Server versions `Users` engine-natively with hidden periods and gives the fragment nothing (no `TemporalAsOf`/`TemporalAll` on `NorseUser` there, accepted for Identity only); on PostgreSQL the opt-in is a no-op. `user_claims` stays temporal under the rule that claim values never carry PII.
- **Non-temporal, and this is a ruling (Himinbjörg#47 Q4, 2026-08-05; amended by the 2026-10-24 spec):** `user_credentials` (the `NorseUser` fragment: `PasswordHash`, `SecurityStamp`, `AccessFailedCount`, `LockoutEnd` and the two HMAC blind indexes — credential, lookup and rate-limiter churn, and *anything computed under a platform key never enters history*), `NorseUserLogin` (`provider_key` is a plaintext third-party subject id forming the primary key, so it can't be encrypted or blind-indexed out of history; link/unlink history moves to receipts, #55), `NorseUserToken` (superseded secrets must not survive in history), `NorseUserPasskey` (`SignCount` churn), `NorseOpenIddictAuthorization`/`NorseOpenIddictToken`/`NorseOpenIddictSession` → `authorizations`/`tokens`/`sessions` (bulk-pruned runtime state), `SubjectKey` (a temporal `DELETE` would preserve the wrapped DEK and make crypto-shredding reversible), `ConsumedPasskeyChallenge` → `consumed_passkey_challenges` (a nonce ledger, pruned as it is written, never history), `VerificationCursor` → `verification_cursors` (a runtime traversal position, never history). **Secret material never archives to history.** Both sides are pinned by `NorseIdentityTemporalModelTests`, including a closing fact that no other entity carries the stamp — changing a marker without amending the ruling breaks tests by design — and on the live catalog by `NorseIdentityTemporalApparatusContainerTests` (PostgreSQL) and `SqlServerIdentitySchemaTests`.
- **Lockout and credential churn ride `user_credentials`, never `users`:** a wrong password, a password change, a stamp rotation and a lockout each write zero `users_history` rows. `Failed_password_writes_no_users_history` pins it on both providers (it replaced the pre-split `A_failed_password_attempt_currently_versions_users`); `LockoutEnabled` stays on `users`, because it is admin policy and so identity record.
- **An unchanged phone number is a no-op success** (Train 2 Ruling 47, `../Glitnir/docs/Himinbjorg/specs/2026-10-26-identity-account-lifecycle-over-grpc-design.md` §14): `SetPhoneNumberHandler` compares the stored plaintext (`GetPhoneNumberAsync`, `""` folded to null) ordinally against the write's E.164 value and answers `phone-updated` with no write, no stamp rotation and no sign-in refresh. Load-bearing, not an optimization — the stock `SetPhoneNumberAsync` unconfirms the number and rotates the stamp even when nothing changed. Pinned on both providers by `A_confirmed_phone_saved_unchanged_stays_confirmed_and_writes_no_users_history`.
- **Email is the username, enforced by the database:** both blind indexes are `NOT NULL` and `user_credentials` carries `CHECK (normalized_email = normalized_user_name)`. EF can't declare a CHECK on a split-table fragment, so it is declared through Urðarbrunnr's `HasFragmentCheckConstraint` seam, which both providers' migrations generators emit on the fragment table. The unique index on `normalized_user_name` therefore *is* email uniqueness. `RequireUniqueEmail = true` on the production registration path makes Identity's own validator refuse an email-less user (`InvalidEmail`) before any write. `NorseUserManager.SetEmailAsync`/`ChangeEmailAsync` set `Email`, `UserName`, both hashes and the stamp in one flush (one `users` version), and translate the store's `DuplicateUserName` into `DuplicateEmail`; `SetUserNameAsync` is refused with `UserNameIsDerived` (`NorseUserManager.UserNameIsDerivedErrorCode`) and writes nothing.
- **`NorseUserStore` implements the `IUser*Store` interfaces directly — no `UserStore<…>` base, no change tracker** (platform NoTracking stays law). Every `FindBy*` reads the whole entity untracked and registers a per-instance as-read baseline (a static `ConditionalWeakTable`, not an identity map); an instance without one is refused by `UpdateAsync`. Mutating store calls stage typed intents; `UpdateAsync` diffs plaintext against the baseline and flushes explicit statements — the `users` update guarded by `concurrency_stamp`, the `user_credentials` CAS, one statement per child intent (savepoints around login and passkey inserts) — in one transaction under a zero-retry strategy (`ZeroRetryExecutionStrategy`; never blind replay). Unchanged columns never appear in a `SET`, and an empty diff touches nothing. A definite failure leaves the instance exactly as read. The immediate operations — the access-failed increment and recovery-code redemption — are raw single statements, each in its own committed transaction, never staged and never repeated. The commit-outcome contract is definite vs `Indeterminate` (`Store/CommitBoundary.cs`): a failed commit is resolved by the stamp marker, by a rollback probe on SQL Server or by `pg_xact_status` on PostgreSQL; what can't be resolved answers `IndeterminateOutcome` (or throws `IndeterminateWriteException` from the immediate operations) and poisons the instance until re-read. `DeleteAsync` is refused in favor of `ShredAsync`, `GetUsersForClaimAsync`/`GetUsersInRoleAsync` are refused (subject-singular law), and `IQueryableUserStore` is not implemented.
- **Norse callers see `Outcome<T>`, never `IdentityResult`, `SignInResult` or OpenIddict exceptions.** Every handler, service and endpoint goes through a `.Outcome` view (`userManager.Outcome.ChangeEmailAsync(…)`), with one mapping table in `IdentityOutcomeMap` (every pinned `IdentityErrorDescriber` code mapped explicitly, unmapped → `Fault`, `IndeterminateOutcome` → `Indeterminate`, `KeyDestroyedException` → `Erased`). `No_handler_service_or_endpoint_calls_raw_Identity_or_OpenIddict_manager_methods` (an IL scan) enforces it over the whole of `Identity.Web.Server`, the external-login callback page included: `Components/` is gone, and with it the scan's last exemption beyond the managers, the framework-boundary adapters and the `SignInManager` view. The managers themselves stay stock. **Framework-boundary adapters stay where they are:** `NorseSignInManager.ValidateSecurityStampAsync` folds a destroyed key to `null` and `IdentityRevalidatingAuthenticationStateProvider` folds it to "invalid", both classifying through `IdentityOutcomeMap.IsErased` — the framework calls them directly, never through `.Outcome`.
- **No token-bearing log line outside `Development`.** A reset link, a reset code and a confirmation link are credentials, and Midgard's service defaults export formatted logs through OpenTelemetry. `AddNorseAuthenticationService` resolves `IEmailSender<NorseUser>` per environment: `DevelopmentEmailSender` (logs each link and code verbatim, by design) under `Development` only, the silent `IdentityNoOpEmailSender` everywhere else. A host wiring a real sender registers its own afterward and wins. `ServiceCollectionExtensionsTests` enforces it (`Outside_Development_nothing_token_bearing_is_logged`).
- **The last sign-in method is guarded under the row lock** (account-lifecycle spec §5.9): `FlushExecutor`'s `RemoveLogin` arm reads the password under a `FOR UPDATE` / `UPDLOCK, HOLDLOCK` lock on the user's `user_credentials` row, counts the logins that would *remain*, and refuses a removal that would leave neither a password nor a login with `LastSignInMethod` → `Conflict`; removing a login the user doesn't have leaves the count unchanged, so it stays a no-op. On the manager path the stamp CAS already serializes stale instances; the lock serializes any flush the CAS doesn't cover, so the count is authoritative. The page hiding the button is not the guard — the wire doesn't hide it. `LastSignInMethodSuite` pins it on both providers.
- **The external-login GETs are the only Account HTTP surface** (`MapNorseExternalLoginEndpoints`): the sign-in start `GET /Account/PerformExternalLogin?provider=&returnUrl=`, the link start `GET /Account/Manage/LinkExternalLogin?provider=` and `GET /Account/Manage/LinkExternalLoginCallback`; the manage group requires `AuthNPolicies.Account`. Both starts are antiforgery-free and fail closed on Fetch Metadata (T3-34): only `Sec-Fetch-Site: same-origin` or `none` challenges, and an absent header, any other value, an unknown provider or a scheme with no display name challenges nothing — the sign-in start returns to `/Account/Login` with the `ReturnUrls.Resolve` landing, the link start redirects with `external-login-failed`. Providers are typed `AddOpenIdConnect` schemes from `Identity:ExternalProviders` (`AddNorseExternalProviders`), sharing only the remote-failure handler. A provider name outside `[A-Za-z0-9_-]+`, or one whose derived `signin-`/`signout-`/`signout-callback-` paths collide with another provider's or a reserved platform path (`ExternalLoginRoutes.All`, `/Account/ExternalLogin`, the stock OIDC paths), fails at registration. No scheme reads the user-info endpoint, and every claim action onto `email` or the name identifier is removed (the stock `sub` action stays, mapping only `sub`, and claim actions run only over user-info anyway), so neither the key nor the email can come from anything but the id token. The provider's return leg has no gRPC answer, so the link outcome rides the redirect to `/Account/Manage/ExternalLogins` (T3-6): `?status=external-login-added` on success, `?status=external-login-not-added` only for a login already associated elsewhere, `?status=external-login-failed` on every other definite failure, and no status key on an `Indeterminate` link, so the page lists the truth on load. The callback clears the external cookie on every exit. The sign-in return leg lands on the static-SSR callback page `ExternalLogin/ExternalLoginCallback.razor` (`/Account/ExternalLogin`), which reaches Identity only through `.Outcome` views and always asks for the second factor (T3-18): `NorseSignInManager.ExternalLoginSignInAsync` throws on `bypassTwoFactor: true`, and the page clears the external cookie before the challenge redirect. A login no account has registers only under the provider's own verified email (closing pre-account hijacking: a typed address would let anyone plant their provider login on a victim's email, surviving the victim's later confirmation or reset). The decision never comes from the claim set (claim lookups ignore case, and a claim name is the token issuer's to spell): `AddNorseExternalProviders`' `OnTokenValidated` reads the validated id token itself (`ExternalProviders.RecordVerifiedEmail`, by ordinal claim name) and, only for exactly one non-empty string `email` and exactly one `email_verified` reading `true` (any casing), writes that address into the external ticket's protected `AuthenticationProperties.Items` under `ExternalProviders.VerifiedEmailItem` (`Norse.Identity.VerifiedEmail`), removing the item otherwise; no token claim can write properties. The same event binds the login's provider key: RC3 `GetExternalLoginInfoAsync` keys the login on the principal's first `ClaimTypes.NameIdentifier` ahead of `sub`, matched ignoring case once the external cookie round-trips, so `ExternalProviders.BindProviderKey` removes every name-identifier claim in any casing from every identity (by predicate: the handler's `CaseSensitiveClaimsIdentity` matches `FindAll(string)` ordinally) and adds exactly one from the token's single ordinal `sub`; a token without exactly one non-empty `sub` fails the remote sign-in to the fixed `RemoteError` (IdentityModel itself refuses an array or object `sub`, reads a numeric one as its string, and keeps the lexically last duplicate). The callback reads only the `VerifiedEmailItem` property (`ExternalLoginInfo.AuthenticationProperties`), then parses it as an `EmailAddress`; no email claim is mapped. Duplicate `email` members resolve, as RFC 7519 §4 permits, to the lexically last (IdentityModel's parse); a JSON array of two refuses. A missing, non-`true` or unparseable email renders "Your sign-in provider did not share a verified email address. Register with a password, then link this provider from your account." and creates nothing, on a registration post as on the render (the refusal renders in place, never the framework's 400 for an unrendered form). Otherwise the form shows the email read-only and the post re-reads the protected item, never a posted value or a claim; the page creates a new unconfirmed, passwordless user (never linking an existing account), adds the login, sends the confirmation link and signs in. A failed login add after the create erases the new user through `ErasureService`.
- **Passkeys: user verification required, every ceremony sealed and bound** (T3-15, T3-31–T3-33). `IdentityPasskeyOptions.UserVerificationRequirement = "required"` (a `PostConfigure`, so no host `Configure` can relax it), so an assertion is possession plus inherence and an authenticator without UV cannot register. The base `SignInManager` passkey members park the ceremony state in the partial two-factor cookie a circuit cannot write, so the IL scan bans all five by name and `NorseSignInManager` runs both ceremonies under its own names: registration through `CreatePasskeyOptionsAsync`/`AttestPasskeyAsync`, sign-in through `CreatePasskeyRequestOptionsAsync`/`PasskeyAssertionSignInAsync`. The ceremony state rides the ceremony itself (`PasskeyCeremony.State`), data-protected and time-limited under a purpose of its own per ceremony, so a registration's state fails an assertion and the reverse. An assertion is one-shot: its state is burned in the `consumed_passkey_challenges` ledger (`PasskeyChallengeLedger`: the SHA-256 of the raw state, one set-based conditional insert after one pruning `DELETE` that keeps rows for `SkewMargin` (5 minutes) past their expiry, so a state still valid under clock skew cannot replay; a lost acknowledgement reads as a replay, so it fails closed) before the handler sees it. Attestation is not one-shot, but `AddPasskeyHandler` binds the ceremony's user entity to the caller (another account → `Forbidden`, nothing saved) after the server-side cap of 100 (`Conflict`). **Passkey sign-in does not ask for the second factor** (`PasskeyAssertionSignInAsync` signs in with the framework's recorded `bypassTwoFactor: true`): a passkey with user verification required is itself a phishing-resistant multi-factor credential (possession plus PIN or biometric), whereas an external provider's assertion carries no second factor, which is why external login always asks for it. This is a controller ruling (2026-10-28) the owner can flip: it is one argument, pinned by `A_two_factor_account_signs_in_without_the_challenge`. Every credential refusal collapses onto one static `SignInRefusal` instance.
- **New recovery codes survive the forced reload in a one-shot handoff** (T3-12, T3-35). `EnableAuthenticator`, `ResetAuthenticator` and `DisableTwoFactor` rotate the stamp, so each re-reads the user and refreshes the sign-in even when a later step fails (never from a poisoned instance) and answers `NavigationResult`. The codes an enable issues ride its `NextUrl` as a `RecoveryCodesHandoff`: data-protected, five minutes, bound to the user and the stamp read after the writes, and revealed once by `/Account/Manage/ShowRecoveryCodes` (`RevealRecoveryCodes`, which burns it in the same ledger and requires the same user, the same stamp and an unchanged stored set). The authenticator issuer is required configuration (`Identity:Authenticator:Issuer`, `AuthenticatorOptions`, `ValidateOnStart`, no code default; only new enrollments read it), and `GetAuthenticatorSetup` provisions a missing key without rotating the stamp through `IAuthenticatorKeyProvisioning`.
- **Only `ReturnUrls.Resolve` decides a landing** (T3-2). A client-supplied `returnUrl` is honored only when it is unambiguously local under the live `PathBase`, judged on the path before its first literal `?` or `#` with nothing normalized and then accepted, and when it is no external-login route (`ExternalLoginRoutes`: a landing that is itself a start would launder a cross-site start past the Fetch-Metadata check); everything else lands on the app root. Every sign-in path parks its resolved landing through `ParkedReturnUrl` for the challenge to carry. `GetSignInMethods` (T3-38) authors every link between the sign-in pages: the password and passkey pages and one start URL per displayed external scheme, each carrying only the resolved landing.
- **The authorize endpoint is Norse's, one source, ambiguity refused** (OpenIddict step-up spec §5.1–§5.3, Task 4.4). `AddNorseIdentity`'s server enables authorization code + PKCE (S256 only: `CodeChallengeMethods` is cleared to S256, since no builder method narrows it), refresh and client_credentials; registers `openid`/`offline_access`; sets code 5 min, access and id tokens 10 min, refresh 14 days rolling, zero reuse leeway; and calls `AddNorseGrantBoundary()` (PF1). The endpoint URIs are relative **without a leading slash** (`connect/authorize`, `connect/token`, `connect/revoke`): OpenIddict joins a relative URI onto `scheme://host/PathBase/` with `new Uri(base, relative)`, so a leading slash drops the `PathBase` and nothing under one would match. Protocol errors carry `error` alone (§5.7, Task 4.7), by one registration per stack, `AddNorseErrorSuppression()`: on the server, `SuppressErrorDetails` clears `error_description`/`error_uri` first on every `Apply*ResponseContext` OpenIddict defines (authorize, token, revocation, and discovery, the key set and every endpoint not enabled, so a later one is covered); on validation, `SuppressChallengeErrorDetails` clears them on `ProcessChallengeContext`/`ProcessErrorContext` just before the header is written, so a `Norse.Bearer` challenge or forbid answers `WWW-Authenticate: Bearer error="..."` and never OpenIddict's diagnostics or its documentation URI (ID2095 on a forbid). `MapNorseOpenIddictEndpoints` maps `/connect/authorize` (GET and POST, passthrough) onto `OpenIddict/OpenIddictAuthorizeEndpoint`, which reads only OpenIddict's request parameters, never `Request.Query`/the form (ASP.NET merges query keys ignoring case, every value kept under one spelling of the framework's choosing, RC3 keeping the later one; OpenIddict stores them ordinally, a repeat as an array, and reads a repeated singular parameter as **absent**, not refused, so `max_age=0&MAX_AGE=999` would read as no `max_age`). So the endpoint refuses `invalid_request`, before minting any marker, a singular parameter that is repeated or spelled in any case but its exact name (I1: the marker, `client_id`, `redirect_uri`, `response_type`, `scope`, `state`, `nonce`, `code_challenge`, `code_challenge_method`, `prompt`, `max_age` and the other OIDC singulars, beside or instead of the exact spelling), and a `max_age` that is not exactly one run of ASCII digits (read raw: OpenIddict's own conversion is lenient). It then follows §5.2's order: authenticate the Identity cookie by name, then **re-read its user through `userManager.Outcome.FindByIdAsync`** (untracked, current; final I1), because the cookie handler re-validates the stamp only once its interval has passed: `NotFound`, `Erased` or a stored stamp other than the cookie's is no principal (challenged, the marker naming no user, or `login_required` under `prompt=none`), so an erased user's surviving cookie mints no authorization or code row and a stamp-rotated cookie never mints a code the exchange would refuse; a lockout is **not** a reason (a locked-out user's valid cookie is still issued a code), and any other read failure is a 500; stale is a missing user id or stamp, or an `auth_time` that is not exactly one integral, unsigned value no more than 5 minutes ahead; re-authentication is required for no principal, stale, `prompt=login`, `max_age=0` always, or `now − auth_time > max_age`; `prompt=none` then answers `login_required`; a bound marker (exactly one exact `norse_reauth`, unprotected, `FixedTimeEquals` on `AuthorizeTransaction.Hash` of the same parameters, the cookie's one `norse_reauth` equal to `MarkerId` `"N"`, its user or none, and burned last in `consumed_passkey_challenges` under the UTF-8 key `"norse_reauth:" + MarkerId("N")`) waives the requirement; otherwise it challenges `Identity.Application` with a re-entry built from the same parameters plus a fresh marker (a POST re-enters as the GET form, T4-7), refusing `invalid_request` instead if `ReturnUrls.Resolve` would not honor it (T4-6). OpenIddict's own refusals (no or `plain` challenge, unknown client, mismatched redirect, `prompt=none` with another value) are 400 pages, never redirects; only the endpoint's own errors redirect with `state`. A non-implicit consent type answers `consent_required`. A code mints `OpenIddict/UserPrincipalFactory` (`sub` to access and id tokens, `NameIdentifier` to access, `auth_time` `Integer64` to both, `norse_stamp` = the cookie's stamp (T4-8) to neither, audience `Norse.User`, never roles, email or name) under one new ad-hoc authorization per request through `authorizationManager.Outcome`. `ReauthMarkers` is one DI singleton the endpoint and `NorseSignInManager` share. `AuthorizeEndpointSuite` pins it on both providers, Heimdall's real login page re-proving a signed-in user included (§6.4).
- **A grant carries its authentication; the token endpoint never re-derives it** (OpenIddict step-up spec §5.4, ruling 11, Task 4.5). `OpenIddictExchangeEndpoint` switches on the three enabled grants (anything else is an `InvalidOperationException`: OpenIddict refused it first); `client_credentials` is the machine lane, unchanged. For `authorization_code` and `refresh_token` it reads the presented grant's validated principal from OpenIddict's own authentication of the request (the transaction's `ProcessAuthenticationContext`, what authenticating the server scheme answers; a scheme-named `AuthenticateAsync` would trip `No_type_that_signs_a_principal_in_reads_an_ambient_principal`, which admits only the Identity cookie's scheme) and requires exactly one `sub` (a `Guid`), one `auth_time` (digits only), one non-empty `norse_stamp` and an authorization id that parses, else `invalid_grant` (the missing authorization id fail-closed, ending what `UnanchoredGrant` can still name); reloads the user through `userManager.Outcome.FindByIdAsync` and answers `invalid_grant` for `NotFound`/`Erased` or a stamp other than the grant's, running `EndGrant` on the presented grant's authorization first (the exchange ends the grant it was handed, never every grant of the user; any other read failure is a 500, never a refusal); **a lockout is not a withdrawal** (Buvy's lockout ruling): a failed-login lockout, which anyone knowing the email can cause, blocks credential sign-in only and neither refuses nor ends an issued code or refresh grant, which still passes PKCE and client binding, expiry, stamp, erasure, authorization status and reuse checks; administrative withdrawal is an explicit stamp change or a grant revocation, never inferred from a lockout date; then mints `UserPrincipalFactory` from the grant's own three facts and scopes on the grant's authorization, so `auth_time` never advances through a refresh. Codes and refresh tokens reach clients as OpenIddict 8 reference identifiers, so a fact reads their claims back through the token manager's payload (`AuthorizeHost.UnprotectAsync`). Errors are the bare `{"error":"..."}` body (§5.7). **`EndGrant` is `OpenIddict/GrantTermination`** (§5.5), registered scoped by `AddNorseGrantBoundary()` and constructor-injected into `RedeemTokenEntryGuarded` and `EndGrantOnReuse` (PF1 closed), which since Task 4.6 take the request's `NorseIdentityDbContext` by constructor too: both are `UseScopedHandler`, so OpenIddict builds them from the request's services and neither resolves anything from `context.ServiceProvider`. Step 1, `GrantStatements.RevokeAuthorizationAsync`, up to 3 attempts, any exception a failed attempt, any row count (zero included) success, and run with `CancellationToken.None` so a client hanging up cannot keep its grant alive, as are the reads that decide whether it runs (M2: `EndGrantOnReuse`'s status read, `UnanchoredGrant`'s link read, the exchange's user read); every attempt failing logs Error `GrantEndUnconfirmed` (authorization id only), adds 1 to `norse.identity.grant_end_unconfirmed` on the `Norse.Identity` meter and answers `Unconfirmed`, and the caller still refuses. Step 2, `tokenManager.Outcome.RevokeByAuthorizationIdAsync`, runs only after a confirmed step 1; its failure, as an `Outcome` or an exception, logs a Warning and still answers `Confirmed`. Erasure needs no `EndGrant`: `ErasureService` deletes the tokens, sessions and authorizations, and a redemption afterward is refused. `TokenEndpointSuite` and `GrantTerminationSuite` pin it on both providers.
- **The guarded redemption is the backstop, and the boundary fails closed** (OpenIddict step-up spec §5.5, §10.6, §10.7, Task 4.6). `RedeemTokenEntryGuarded` replaces OpenIddict's `RedeemTokenEntry` at its order with one statement (`GrantStatements.RedeemAsync`: `valid` → `redeemed` only while the token's own authorization is `valid`), autocommitted, under `ZeroRetryExecutionStrategy`: one row proceeds; zero rows is reuse, so `EndGrant` runs and the request answers `invalid_grant`; any database exception propagates unhandled (HTTP 500, nothing minted, never retried, never `EndGrant`). A definite failure (a connection that never opened) leaves the token `valid` and it refreshes afterward; an indeterminate one (the acknowledgement lost after the commit) leaves it `redeemed`, so the client's retry is reuse and ends the grant. `EndGrantOnReuse` carries no id filter: a code or refresh token reaching it, `RedeemTokenEntryGuarded` or the token endpoint's step 1 without a token id or an authorization id that parses is refused (`invalid_grant`; `invalid_token`, normalized to 200, at revocation), never passed through, after `OpenIddict/UnanchoredGrant` ends what can still be named (the presented authorization, else the one the token's row links, else nothing). **Revocation is OpenIddict's own** (§5.5, Task 4.7: v8 has no revocation passthrough, and `EnableErrorPassthrough` stays off): RFC 7009 under the grant boundary. A `valid` refresh token is revoked alone and the authorization stays `valid`; a not-`valid` code or refresh token presented there is reuse, so `EndGrantOnReuse` ends the grant and the answer is the normalized 200; a `valid` code answers `unsupported_token_type` (400) and changes nothing; an access token is marked `revoked` and ends no grant. An unknown, expired, revoked or redeemed token answers what a successful revocation answers, identical in status, content type and body (200, `{}`; headers are not compared). Client authentication follows the client's type: a public client by `client_id` alone, a confidential client only with its secret (`invalid_client`, 401, otherwise). No OpenIddict endpoint answers an `Outcome`/`Problem` envelope. `RevocationSuite` pins it on both providers. `GrantBoundarySuite` pins every §10.6/§10.7 interleaving through the production endpoints on both providers, driven by the named `PausePoints` (`BeforeRedemption`, `AfterRedemption`, `BeforeValidateTokenEntry`; never sleeps, never one barrier), with the production `GrantTermination` behind a journal that asserts the authorization each grant end resolved; the redemption-failure facts run the handler over a context of their own (`RedemptionFailureInterceptor`: the statement has no transaction, so `CommitFailureInterceptor`'s commit hooks never see it).
- **The stranded-account verification runs in the web host** (T3-28; Glitnir §2.2). `AddNorseIdentityInvariantVerification` registers `IdentityInvariantVerificationService`, a `BackgroundService` Yggdrasil's web server hosts (`Identity:Verification`, with an `Enabled` switch; an `Interval` over one day fails at startup). It walks every account, never a sample, by an ordered keyset over the id, from a persisted cursor in `verification_cursors` that wraps at the last page and advances by compare-and-set on its version, written through `ProviderStatements`, so replicas share it and a lost advance only reads a page twice. The bound is the code's, no stronger: for a stable account population every account is visited within ceil(N / `SampleSize`) successful advances counted from a traversal start, or ceil(N / `SampleSize`) + 1 from a cursor in the middle of a page, across however many replicas run; concurrent inserts, deletions, failures and restarts rule out a fixed-run guarantee, and none is claimed; a restart forgets the pending candidates and delays their report until the next traversal. A candidate with neither a password nor a login is reported (Critical) only when the next run's explicit recheck still finds it stranded, so the `CreateAsync`→`AddLoginAsync` window never reports. A failed run logs an Error, keeps its pending set and never stops the host.
- **The OpenIddict pruner removes runtime rows in foreign-key order** (OpenIddict step-up spec §5.6, Task 4.8). `AddNorseIdentity` registers `OpenIddict/OpenIddictPruningService`, a `BackgroundService` on the injected `TimeProvider` (`Identity:OpenIddict:Pruning`: `Enabled`, `Interval` 1 hour in (0, 1 day], `MinimumAge` 14 days, all validated on start; the `MinimumAge` floor is the refresh lifetime read from `OpenIddictServerOptions`, never a copied constant, and an unbounded refresh lifetime fails it, because a redeemed refresh token pruned while still replayable would turn reuse into an unknown token). It runs at startup and every interval, one scope per run, and prunes through the `.Outcome` views at one threshold (`now − MinimumAge`): tokens, then sessions, then authorizations, the schema's order (`tokens` reference `sessions` and `authorizations`, `sessions` reference `authorizations`, none cascades; OpenIddict's authorization prune checks for tokens but not sessions, so authorizations before sessions would fail on the session's key — the spec's tokens → authorizations → sessions is an erratum). What each step removes is OpenIddict 8's own `PruneAsync` (decompiled preview.4): tokens created before the threshold that are expired, neither `valid` nor `inactive`, or under a no-longer-`valid` authorization; sessions not `valid` with no token; authorizations ad-hoc or not `valid` with no token. A step answering a failed outcome ends the run (Error, `StepFailedEventId`); an exception is caught at the per-run boundary (Error, `FailureEventId`), and the next tick retries; host cancellation still propagates. `PruningSuite` pins it on both providers, `OpenIddictPruningServiceTests` the loop and the options. The fixture and the OpenIddict test hosts stop before they dispose, so the pruner ends as a host stop ends it.
